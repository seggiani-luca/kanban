\noindent
\textbf{Documentazione kanban v0.0} \hfill 2025 - Luca Seggiani

\section{Morale}
Si presenta l'implementazione di un’applicazione distribuita che realizza il metodo di gestione del lavoro basato su \textbf{kanban}.
I principi che si sono voluti seguire in fase di sviluppo sono:
\begin{itemize}
	\item Protocollo di trasmissione livello \textit{application} basato su stringhe ASCII separate da ritorni carrello (\lstinline|\n|), leggibili da uomo, ispirato a SMTP. Queste stringhe vanno a rappresentare i \textit{comandi} dell'applicazione in maniera espressiva e su cui è facile fare debugging;
	\item Comandi fra server e client inviati su TCP, comandi fra client inviati su UDP (con minima affidabilità basata su ritrasmissioni). L'uso di socket TCP e UDP sulla stessa porta permette di discriminare gli utenti per porte anche nelle connessioni peer-to-peer;
	\item Design \textit{modulare}, dove si divide la funzionalità in appositi moduli \lstinline|core|, \lstinline|net|, ecc... lato client e server, per maggiore leggibilità; 
	\item Approccio il più semplice possibile: no allocazioni sull'heap, client e server ciascuno su un unico thread di esecuzione Questo è stato fatto per aumentare la robustezza del codice e ridurre la possibilità di errori, con il contro di minore scalabilità. 
\end{itemize}

\section{Costanti e strutture condivise}
Esistono alcune strutture condivise fra client e server: queste vengono definite una sola volta per evitare di riprodurre codice.
\begin{itemize}
	\item \lstinline|card/|: definisce il tipo \lstinline|card| di una kanban:
\begin{lstlisting}[language=C++]	
typedef struct {
  card_id id;								// id (se e' 0 la card e' nulla)
  char desc[CARD_DESC_LEN]; // testo attivita'
  int user;									// utente che la sta implementando o l'ha implementata
  struct tm timestamp;			// timestamp dell'ultima modifica
} card;
\end{lstlisting}

Le card gestite dal server vengono allocate in una pool statica definita in \lstinline|server/pool.h|: si possono ottenere e liberare nuove card con le funzioni \lstinline|alloc_card()| e \lstinline|free_card(card *p)|, dalla semantica simile alle \lstinline|malloc()| e \lstinline|free()| della \lstinline|stdlib|. Questo permette di evitare allocazioni sull'heap, riducendo la complessità e il rischio di perdite di memoria.
Puntatori a card vengono organizzati in un'apposita matrice che rappresenta le colonne della lavagna: \lstinline|card *columns[NUM_COLS][MAX_CARDS_PER_COL]| in \lstinline|server/core.h|.
	\item \lstinline|cmd/|: definisce il tipo \lstinline|cmd| per i comandi scambiati fra client e server, e fra più client in modalità peer-to-peer:
\begin{lstlisting}[language=C++]	
typedef struct {
  cmd_type type;									// tipo di comando
  const char *args[MAX_CMD_ARGS];	// argomenti del comando, in una lista terminata da NULL
} cmd;
\end{lstlisting}
Per comodità si è scelto di rappresentare gli argomenti come una lista di puntatori a stringhe, terminati da NULL.
Il formato dei comandi in transito sulla rete è generalmente il tipo di comando in maiuscolo. Fanno eccezione i comandi con argomenti:
\vspace{-10pt}
\begin{table}[H]
	\center
	\begin{tabular} { p{5cm} | p{10cm} }
		\bfseries Comando & \bfseries Formato \\
		\hline
		CREATE\_CARD & \lstinline|CREATE_CARD <id> <colonna> <descrizione>| \\
		ACK\_CARD & \lstinline|ACK_CARD <id>| \\
		MOVE\_CARD & \lstinline|MOVE_CARD <id> <colonna>| \\
		HANDLE\_CARD & \lstinline|HANDLE_CARD <id> <descrizione>| \\ 
		SEND\_USER\_LIST & \lstinline|SEND_USER_LIST <porta> ...| \\
		ACK\_REVIEW\_CARD & \lstinline|ACK_REVIEW_CARD <voto>|
	\end{tabular}
\end{table}
\vspace{-10pt}
I comandi OK, ERR e ACK\_REVIEW\_CARD vengono forniti come ack. A ogni comando può seguire un commento.

	\item \lstinline|core_const.h| e \lstinline|net_const.h| contengono costanti relative rispettivamente ai \lstinline|core| (numero massimo di client, ecc..) e ai moduli di rete (indirizzi, numeri di porta, ecc...).
\end{itemize}

\section{Gestione rete}
L'idea dietro i moduli di rete è che questi separano la logica di lettura e scrittura su socket dai moduli \lstinline|core|, che devono preoccuparsi solo della logica relativa alla kanban. In particolare, abbiamo che:
\begin{itemize}
	\item Le operazioni di \textit{ricezione} (\lstinline|recv()|) avvengono in multiplexing, e quando possibile. Ciò significa appena si ha tempo per il server, e quando si hanno \textit{"momenti morti"} per il client: e.g. quando si fanno richieste o quando si va in attesa simulando l'elaborazione delle card. Il contro di questo approccio è che si possono avere lievi imprecisioni temporali per la gestione dei timer del server;
	\item Le operazioni di \textit{invio} (\lstinline|send()|) sono sincrone e bloccanti, in quanto la mole di comandi inviati è ridotta.
\end{itemize}

Il compito vero e proprio dei moduli di rete è quindi schematizzabile come segue:
\begin{enumerate}
	\item Ottenere linee separate da \lstinline|\n| dallo stack di rete del sistema operativo e deserializzarle in comandi;
	\item Smistare tali comandi fra i vari moduli. Questo si fa sfruttando una mappa definita sui tipi comando:
\begin{lstlisting}[language=C++]	
typedef enum {
  CORE,  // comandi standard
  WATCH, // comandi di controllo client (PING_USER, PONG_LAVAGNA)
  PEER   // comandi di revisione fra peer (REVIEW_CARD, ACK_REVIEW_CARD)
} mod_type;
\end{lstlisting}
	\item Inviare indietro risposte, serializzate da comandi, ottenuti sempre dai moduli.
\end{enumerate}

\section{Server}
Per il server questa corrispondenza è diretta, in quanto tutti i comandi ricevuti sono provenienti da client, e il modulo di rete deve quindi limitarsi a smistarli fra modulo \lstinline|core| e modulo \lstinline|watch|.
Non esiste quindi una funzione \lstinline|recv()|, ma una \lstinline|listen_net()| che gestisce in multiplexing le richieste arrivate al server, oltre che ai timer usati per gestire il modulo \lstinline|watch|.
Questa si basa sulla \lstinline|select()|:
\begin{lstlisting}[language=C++]	
void listen_net() {
  // gestisci i timer
  for (int i = 0; i < MAX_CLIENTS; i++)
		handle_timer(&connections[i]); // sostanzialmente un tick del timer

  // scansiona con la select
  select(fdmax + 1, &read_set, NULL, NULL, &tv);

  for (int i = 0; i <= fdmax; i++) {
    // controlla che si qualcosa da leggere
    if (!FD_ISSET(i, &read_set))
      continue;

    if (i == listen_sock) { 				// accetta nuovo client
      accept_client();
    } else if (i == STDIN_FILENO) {	// gestisci console amminisratore
      handle_client(&admin_conn);
    } else {												// gestisci client
      handle_client_sock(i); // chiama handle_client()
    }
  }
}
\end{lstlisting}
Notiamo che si prevede un client speciale, con socket \lstinline|STDIN_FILENO|, inteso come l'"amministratore".
Ne si prende il controllo interagendo con la riga di comando offerta dal server stesso, e viene fornito per spostare card e crearne di nuove.
Si rende poi disponibile una \lstinline|send_client(client_id cl_id, const cmd *cm)|.
La gestione dello stato del sistema e delle card è delegata al modulo \lstinline|core|, che deve solo portare avanti l'operazione richiesta sulla base del tipo di \lstinline|cmd| fornito in \lstinline|handle_command(client_id cl_id, const cmd *cm)| (chiamata da \lstinline|handle_client()|). Notiamo poi che i moduli\lstinline|net| e \lstinline|core| del server usano astrazioni diverse per i client, in modo da mantenere in ogni modulo solo l'informazione necessaria. 
Un client per il modulo rete è rappresentato da una \textit{connessione}:
\begin{lstlisting}[language=C++]	
typedef struct {
  int sock;											// socket della connessione (se e' 0 la connessione e' nulla)
  unsigned short port;					// porta della connessione
  char read_buf[CMD_BUF_SIZE];	// buffer di lettura
  int read_len;									// caratteri letti in buffer
} connection;
\end{lstlisting}
mentre nel modulo \lstinline|core| si mantiene informazione relativa allo stato dell'utente, alle card fornite, e di utilità al modulo \lstinline|watch|:
\begin{lstlisting}[language=C++]	
typedef struct {
  client_id id;									// id (se e' 0 il client e' nullo)
  client_sts sts;								// stato
  card *handling;								// puntatore alla card che sta gestendo (se e' NULL sta aspettando una card)
  struct timespec deadline;			// deadline del timer
  int sent_pong;								// un flag che rappresenta se si sta aspettando un ping dal client
} client;
\end{lstlisting}

Si nota la stretta dipendenza fra il modulo \lstinline|watch| e il modulo core: per facilitare la loro interoperazione quest'ultimo fornisce appositamente due header, \lstinline|core.h| e \lstinline|core_watch.h|, di cui il secondo più intimo e riservato al modulo \lstinline|watch|. 

\section{Client}
Per il client si ha una complicazione data dal fatto che è il modulo \lstinline|core| a portare avanti l'elaborazione, effettuando operazioni di ricezione e invio su propria discrezione.
Allo stesso tempo, il modulo di rete deve essere pronto a gestire comandi provenienti sia dal server che da altri client, e questi comandi potrebbero dover essere gestiti da uno qualsiasi fra i moduli core, \lstinline|watch| e \lstinline|rev|.
Per questo si rende disponibile una funzione \lstinline|recv_multi(cmd *cm, int block)|, che gestisce in multiplexing le richieste, e smista finché non si ottiene un comando diretto al modulo core. In tal caso si restituisce il comando, rimandando alla prossima chiamata le gestione delle richieste successive. 
Il flag \lstinline|block| permette inoltre di specificare se si vuole che la funzione blocchi fino alla ricezione di un comando diretto a core, o se si vuole uscire dopo un timeout di 1 secondo (usato per l'implementazione dell'attesa casuale).
Con questo approccio si riescono a gestire le richieste dirette al client nei \textit{"momenti morti"} accennati sopra:
\begin{lstlisting}[language=C++]	
int recv_multi(cmd *cm, int block) {
  while (1) {
    // scansiona con la select
    if(select(fdmax + 1, &read_set, NULL, NULL, block ? NULL : &tv) == 0) return 0;

    // c'e' qualcosa sul socket UDP?
    unsigned short who;
    if (FD_ISSET(udp_sock, &read_set))
			recv_peer(&who, cm);
      if (handle_cmd(who, cm) > 0)
        return 1; // e' core, esci

    // c'e' qualcosa sul socket TCP?
    if (FD_ISSET(tcp_sock, &read_set))
			recv_server(cm);
      if (handle_cmd(0, cm) > 0)
        return 1; // e' core, esci
  }
}
\end{lstlisting}

Si rendono poi disponibili una \lstinline|send_server(const cmd *cm)| per l'invio a server e una \lstinline|send_peer(unsigned short who, const cmd *cm)| per l'invio a peer.
L'implementazione del client diventa quindi semplice: basta chiamare la \lstinline|recv_multi()| per il prossimo comando \lstinline|core|, con gli altri comandi gestiti dietro le quinte. Vediamo a scopo di esempio come ci si registra al server:
\begin{lstlisting}[language=C++]	
int hello() {
  // richiedi registrazione
  cmd cm = {.type = HELLO, .args = {"richiedo la mia registrazione"}};
  send_server(&cm);
	
  // attendi ack
  cmd rep = {0};
  int ret = recv_multi(rep, BLOCK);
	return rep.type == OK;
}
\end{lstlisting}
Funzioni di questo tipo (definite nel modulo \lstinline|core| del client) vengono chiamate in un loop che ottiene card, aspetta un tempo casuale, richiede i peer e li interroga per le revisioni, e restituisce la conferma di aver processato la card al server.

\section{Compilazione}
Si rende disponibile un Makefile per la compilazione con \lstinline|make|. \lstinline|make| viene usato anche per avviare dei test:
\begin{lstlisting}[language=python]
# compila la lavagna 
make lavagna

# esegue la lavagna con un set di card predefinito, specificato nel file dat/cards.txt
make run_lavagna

# compila il client
make client

# esegue 4 client
make run_clients

# esegue un client su una certa porta
make run_client ARGS="<porta>"

# ripulisce gli oggetti
make clean
\end{lstlisting}
